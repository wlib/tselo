# The store: identity, derived state, compiler as library, views

Programs, contracts, models, evidence, histories, and decisions live in one logical store that is content-addressed, incrementally derived, and frontier-tagged, physically distributed and often absent at runtime. Syntax, files, and names are views. The compiler is a library of participants in the derivation graph. The shared, cross-party form is the [Claim store](claim-store.md).

## Identity

Content addressing dissolves version hell (names are not identities; every definition is its hash; versions coexist; an upgrade is an edit propagated through dependents; the diamond problem disappears at the identity level) and makes compilation cacheable. Five identities stay apart:

| Identity | Names | Consequence |
|---|---|---|
| **represented artifact** | these bytes or this canonical structure | a hash is identity of a representation, not semantic equivalence |
| **editing** | the entity the author works on across edits and renames | renaming must not invalidate machine code; editing must not lose which entity was edited |
| **optimized artifact** | a specific output | reuse depends on assumptions and context (target, cost-model version, established facts), not only the body hash; input- vs content-addressed derivations are this distinction |
| **semantic relationship** | two artifacts equivalent or related under a contract | proved, not hashed; different hashes can implement one contract |
| **instance** | this running actor, deployed copy, manufactured part | connected to its model by measurements and calibration |

Across fragments the primitive relation is the certified edge, and equivalence classes are a derived view ([Claim store](claim-store.md)). Hot update preserves state only if state is addressed by what it means, not where it sits (Erlang's explicit process state and `code_change` versus React Fast Refresh keeping hook state by position and breaking when hooks reorder). A structural store computes semantic diffs natively, and a diff is an edge between two frontiers; text tools reconstruct diffs with tree differencing. Content addressing does not resolve incompatible protocols or two versions managing one external state (C42; [Change](change.md)). Open: canonicalization boundaries, stable references through edits, recursive definitions, which metadata belongs in hashes and invalidation keys, merge semantics, sharing without exposing private source or models (Q07, Q08).

## Compilation is derived state

The reference semantics is the source of truth, compiled tiers are materialized views, inline-cache feedback is an input stream, guards are invalidation predicates, deopt abandons a speculative branch, on-stack replacement is a derivation catching up to a frontier mid-iteration, the article's skip-list snapshots are cached specializations at different assumption levels, and fleet profiles are inputs to the same graph ([Correspondences](correspondences.md)). "Mixed and dynamic" tradeoff management is then a choice of where in the graph to materialize and with what staleness. One derivation discipline (demand-driven, frontier-tagged, invalidation predicates, provenance) serves the authorizer's rewrites, the e-graph, materialized views, type-constraint propagation, index selection, and profile aggregation under several cost models; compiling a policy into database functions is a lowering of the same kind.

Three qualifications are load-bearing. **Activation is not derivation**: the graph produces an artifact; installing it is a transition with effects, state translation, coordination, and temporary resources ([Change](change.md)). **One meaning, many materializations** (C-store): the logical system is one; its physical implementation is distributed, selectively replicated, summarized, and sometimes absent, so a small controller receives a specialized implementation and a compact configuration, not the derivation history, and controllers need compatible meanings and exchange protocols rather than one store or the same facts. **Semantic is not artifact identity**: context-dependent optimization is not globally reusable for free. Transformations state their input/output relation, preconditions, evidence, residual obligations, and activation cost; search may preserve alternatives rather than commit to one phase order.

## The compiler as a library

Daniel's ask: use the compiler and optimizer like a library, with custom lowerings and checks unified with the type system, and gradual control of any aspect of compilation on any part of the code. The pieces exist, scattered ([Systems](../evidence/systems.md)). What is missing: the dials are held by language implementers rather than authors (speculation annotations and tier-up policy live inside the VM); lowering is a fixed pass pipeline rather than search over a fact base; placement and hierarchy are not yet in the type system of a language people use (OxCaml's modes are the first mainstream step, Regent-style privileges on regions the next); the cost model is hand-written per kernel rather than supplied by the hardware ([Participation](participation.md)); and the mapper's dial is not in the author's hand, scoped ([Commitment](commitment.md)).

"Library" does not mean plugins executing opaque commands. A contribution is a candidate generator or rewrite rule with its equational justification, a checker, a cost model with a validity domain, a lower-bound provider, a transition planner, or a view, each participating in the derivation graph with provenance and each itself a replaceable artifact ([Change](change.md)). There is no universal engine: equality saturation, polyhedral transformation, staging, partial evaluation, translation validation, and synthesis each have an applicability class depending on semantics and cost. Compilation effort is a resource: cache and reuse evidence, candidates, and models where dependencies permit; choose portfolio search, instrumentation, and lower-bound providers by expected value; distinguish generating an artifact from activating it. At full scope lowering extends past equivalence-preserving compilation to planning, inference, experimentation, and authorized specification change, each step stating which relation it claims ([Realization](realization.md)).

## Views and the editor

Programs are not text. They live in the structured store; syntax, files, and grouping are views that authors and readers declare as metadata, with mixed structural and textual editing; a theory ships its projections, and three readers can see one set of records through a Rust-shaped projection, an equational one, and a dataflow diagram ([Language](language.md)). Diff, review, blame, grep, and language models are text-native, so views serialize to a canonical text form for those tools. Structured storage is motivated by explicit identity, transformations, and multiple editing projections, not by a claim that text is intrinsically lossy; text can encode structure losslessly and comments need not be discarded (C51).

Views are bidirectional with policies: a view supports observation and meaningful edits; an edit proposes a change to the underlying model with declared scope, ambiguity handling, and affected dependencies; a projection is not automatically invertible, lenses fit suitable cases, and arbitrary edits through arbitrary derivations are not uniquely invertible, so edit policies, ownership, and ambiguity handling remain necessary. The article's CMS example gives the general rule: a derivation records *which distinctions it uses* (whether a heading is empty), not just which object it read, and invalidation follows those predicates.

The editor is the primary means of making the design legible. For a component it shows its semantic operations and laws, current representation and placement, the evidence behind the implementation, the measurements and predictions behind its selection, the cost of switching, and the alternatives an author's constraint excludes, so the author's interventions become *this distribution is unrepresentative; this deadline matters more; keep this fixed during the experiment; spend more search here* rather than "turn optimization up". For a change it shows whether it is a proven representation change, a guarded specialization, or a proposed behavior change, with the evidence. For a past decision it shows the model that chose it, under what frontier, and what drift invalidated it; provenance on decisions is the backward map for decisions, and the debugger is this query. The standing question the surface answers for any artifact is *why does this decision still exist*, and the answer is one of: a physical constraint, an admitted observer, a current prediction, a retained option, an unexplored alternative. For any fragment it shows the front of alternatives, the chosen point, the records that justify it, and what would have to change for another point to win; every editor interaction is itself collected under a policy, so the developer experience is a measured front like any library. At full scope views over code and equations, CAD geometry, timelines, simulations, cost tradeoffs, UI mockups, and physical layouts edit the same entities, and the system explains consequences in other participants' views (moving a wall changes structure, wiring, lighting, sequence, and cost); showing multiple views does not ensure consistency, so the coupling must be modeled ([Realization](realization.md)). Views are keyed by editing identity, machine code by semantic identity, cached lowerings by artifact identity.
