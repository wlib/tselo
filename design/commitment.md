# Commitment: binding time, retention, options, standards

Authors progressively constrain the set of acceptable implementations, each commitment scoped and reasoned. Every deferred decision is a retained distinction and every retained distinction is a purchased option, so binding time, retention, and flexibility are one tradeoff from registers to schemas to standards to buildings. A standard is a retention decision at ecosystem scale, and the replacement for the C abstract machine must be a better option, not a better model.

## Gradual commitment

Daniel's "gradual control over any aspect of compilation on any part of the code to any degree" has a precise meaning: authors specify a mathematical result, then pin its numerical semantics ([Quantities](quantities.md)), then layout, then schedule, then a particular cell, each commitment with the fields in [Schemas](schemas.md) and the editor showing what it forecloses. By default none of these is written; they are edges the mapper adds ([Language](language.md)). Kinds are not interchangeable: a hard constraint, a preference, a trusted assumption, a temporary experiment; releasing a layout constraint is not permission to change behavior. Commitments compose as restrictive layers, each shrinking the set of acceptable lowerings; shrinking is not coordination-free when cached decisions depend on the old set ([Irreducibles](irreducibles.md)). The language lets the system exploit the memory hierarchy and lets authors constrain placement where useful, without making everyone program against it.

**Direction is the first commitment.** The store's native content is relations with equational theories; a function is a relation with a direction chosen. Leaving direction to lowering is what lets edits bubble up through derivations (the view-update problem); a lowering with a backward map at safe points is a *partial* lens. Dead-code elimination loses information on purpose, so lowerings need not be invertible, only able to establish a continuation at designated points (C04). Removing a commitment from an existing artifact is uncommitting ([Onboarding](onboarding.md)).

## Binding time = retention = options

To bind later one must keep the information needed to decide later: retention *is* deferral, elimination *is* early binding. A decision can bind at manufacture, configuration, deployment, admission, or execution; an addition can be a dedicated path, a configured datapath, an operation in a spatially scheduled region, an instruction on a shared sequencer, or a distributed computation. All are legitimate lowerings; none defines the architecture. The same ladder applies to routing, memory organization, representation, scheduling, checking, encoding, authority enforcement, and to whether a decision lives in silicon, software, a lookup table, an operator's hands, or a policy document. Bind early → forget → cheap and rigid; bind late → retain → expensive and flexible: two related dimensions connected by future requirements, not a law (C48).

**Flexibility has an information cost.** v1 retains count and sum of integer samples and answers means exactly; v2 adds historical variance; histories `[0, 2]` and `[1, 1]` give identical v1 state and different variances, so no migration function is correct and a larger solver cannot remove the choice. Options: retrieve history from elsewhere; start the statistic at the upgrade boundary with the output type carrying "since t₀"; introduce an explicit approximation or unknown. Keep two questions apart: *was the information retained?* (a full window retains more than count + sum) and *can this implementation compute the new result?* (a fixed datapath may lack the operation even when the information exists). The formal object is a **sufficient statistic** for a declared family of future queries; sliding windows need removal information even for the mean (C44); arithmetic must be specified (C46). Tested by [E3](../experiments/contract-change.md).

**Retention is an explicit variable**, not whatever the implementation happens to keep: history for a declared family of schema changes; selected sufficient statistics; replayable inputs for a bounded period; compatibility state while old clients are active; discard when cost exceeds declared value or when deletion requirements or authority demand it. Event sourcing buys every option at maximal cost and still only those whose information was captured (C49). Existing instances: garbage collection, log retention, expand/contract migrations, a programmable region on a die; retained physical flexibility such as spare conduit in a building is analogous, not the same economic model. The **retention planner** chooses sufficient statistics for a family of admitted future contracts (Q15, Q16).

**Option value.** A replaceable module, retained history, a programmable region, a standard connector each have a present cost and a possible future value the system can price. Preferences do not all fit one number: exact requirements, measurable targets, ranked preferences, examples, human evaluations, and unresolved disagreements are different inputs. Lineage, as related ideas not one theory (C50): Parnas (decompose by what is likely to change, so information hiding is retention planning), monotone co-design (functionality, implementation, resources as composable relations with Pareto fronts, tractable for a monotone class), partial evaluation (binding-time analysis), real options.

## Standards are retention decisions at ecosystem scale

The stack is hacks on hacks not from laziness but because each layer boundary is a treaty letting both sides evolve independently; Daniel's point stands beside it: with the whole stack in scope at once there is no excuse but effort for less than the limit. A standard (interface, format, protocol, ISA, abstract machine) retains an interface distinction across parties and time so independent realizations can bind to it: teams work independently, tooling is reused, one proof covers many implementations, parts stay available for decades. Its cost is local freedom lost and cleverness pushed below the interface where the compiler cannot see it. The C abstract machine was a terrible model and a fantastic treaty: enormous option value, retention cost paid invisibly in hardware honesty (out-of-order cores pretending to be sequential, coherence because programs do not say what moves, Spectre as the bill), fifty years of amortization. Successful renegotiations (CUDA, XLA) narrowed the program class rather than making hardware honest to arbitrary programs.

**The price of the treaties just changed.** Every standing treaty (the C abstract machine, Unix, SQL, TCP/IP, x86) was priced in a world where implementation effort was the scarce input: memory in kilobytes, no profilers, humans typing every realization. Worse-is-better, backward compatibility, and short-term tradeoffs were rational under that price. Daniel's premise ([User intent](../intent/user-intent.md) §2) is that AI makes re-realization cheap, which reprices every treaty at once: an interface retained so strangers need not re-implement is worth less when re-implementation is cheap, and agreement on *meaning* (the store's content) replaces agreement on *interface* as the thing worth retaining. What does not get cheaper is arbitration, trust, and intent ([Irreducibles](irreducibles.md), [Trust](trust.md)), so the design's weight shifts there, and the field's youth (every treaty above is younger than a human lifetime) is a reason to expect the renegotiation to be total rather than marginal.

The replacement must be a better *option*, not a better *model*: lower retention cost because it describes itself instead of freezing what it describes, comparable option value because strangers still evolve independently. The participation protocol is the candidate ([Participation](participation.md)), and what it freezes is an extension mechanism rather than a vocabulary ([Language](language.md)), so the treaty to price is the record format, the judgment, the base theory, and the bridge form (Q53). Procurement sits on the same ladder: buying hardware, scheduling a datacenter, tiering a JIT, and predicting a branch are one decision ladder at different time constants, and capacity planning is optimization at the month scale. Pricing a standard: ecosystem cost plus the sum of lifecycle costs of projects within it, so "use a standard part", "create a reusable part", and "build project-specific" become alternatives with different amortization horizons; the stack can help choose where to standardize, what to leave variable, and how a standard evolves; backward compatibility has a measurable purpose, neither sacred nor wasteful ([Realization](realization.md) for the ecosystem objective). Boundaries are also stable because they let parties work with limited mutual knowledge; redrawing one redraws responsibility.
