# Change: transitions, evolution, residual obligations, self-application

An implementation and a transition between implementations are separate artifacts. One seven-field protocol covers GC, live migration, schema change, hot upgrade, on-stack replacement, accelerator remapping, and fleet rollout. Replacing an implementation under a fixed contract differs from evolving the contract. A running system carries state and obligations. What remains at runtime after everything static is discharged is the residual obligations and nothing else, and the stack's own bookkeeping is subject to the same elimination.

## Implementation and transition

A **contract** is the admitted interactions and required behavior under stated assumptions. An implementation is a replaceable, inspectable explanation of how a contract is realized: what it implements, requires, establishes, with evidence, models, observations, and supported transitions ([Schemas](schemas.md)). Activating one is an operation with effects and obligations; updating a derivation graph does not discharge them.

Every live transition anyone has built (Baker's incremental GC, VM live migration, online schema change, Erlang hot code upgrade, on-stack replacement, RCU, rolling deploys) shows the same seven fields ([Schemas](schemas.md)). The divergence policy is the latency/throughput/memory tradeoff. Publication need not be one instant: version consistency may be promised per session or per transaction, and DNS cutover is not atomic (C22). The commit boundary bounds what translation may undo. Which field dominates differs: state translation for JIT specialization (frame reconstruction), divergence and reclamation for a live index migration, quiescence for an accelerator (a systolic array cannot stop mid-wave). That the protocol is architectural, with only the commit-boundary model and the error contract differing across cases, is a proposed interface tested by [E4](../experiments/transition-contract.md), not a theorem that every update has seven sequential phases. Quiescence is never mandated as "quiesce, serialize, resume"; each component declares which of drain, finish, checkpoint at points, retain old alongside new, and restart it supports ([Participation](participation.md)).

## Two kinds

```text
implementation replacement   a different realization of the same contract
software evolution           an authorized transition between different contracts
boundary operation           moving, splitting, or eliminating a boundary between regions, with its authority
```

Replacement: no permitted observer distinguishes before from after except through declared relaxations; a simulation or refinement argument, not necessarily bisimulation (C06). Evolution: distinguishable behavior is the point, and what needs specification is the transition itself: which old commitments survive, which new rules begin, how existing state acquires its new meaning, what happens to active sessions, how missing information is handled. Type-compatible state is not necessarily semantically correct state (units or meanings can change without a type change); dynamic-update research separates generic conditions (type safety, reachability) from application-specific correctness. Uncommitting beyond an established compatibility contract is evolution even when an agent discovers it ([Onboarding](onboarding.md)).

A **boundary operation** redraws where a region ends: merging two services, splitting a cell, moving a check from a per-operation guard to configured wiring, reorganizing a team. The criterion for where a boundary belongs is the information that must cross it ([Observers](observers.md)); the operation carries the seven fields and one more thing, the transfer of authority over what the boundary separates, because boundaries are stable exactly because they let parties work with limited mutual knowledge ([Realization](realization.md), Q32). Conway's law is this transition kind seen in an organization.

## State plus obligations

A running system has state *and* obligations: accepted requests, active sessions, pending effects, durability promises, resource ownership, callbacks someone is entitled to, scheduled physical actions, compatibility commitments. Each is translated immediately, finished under old code while new requests use new code, or kept behind an adapter. An update that preserves data but drops accepted work is incorrect; a replay that rebuilds state but repeats external effects is incorrect. The clean split is obligations as linear (discharged or handed off exactly once; session types and typestate are the vocabulary) and state as ordinary (C47), with the qualification that cancellation, retries, at-least-once delivery, idempotence, and compensation need explicit protocols and a step boundary is a useful transition point, not an automatically safe one. The article's program model ("state machines with pure functions inside") is why Erlang got hot upgrade for free: every step boundary is a safe point and state is a value for which a transformer can be derived from the type diff.

## Ecosystem evolution

Daniel's requirement: dependencies, how they update, and hot live update from any version to the latest with minimal diff and best state preservation.

- **Dependencies.** Version resolution is NP-complete and belongs with the other pluggable solvers. Semver is a *claim*: the bump can be computed from the signature diff and the ecosystem can be built against a change; generalized, the registry runs pluggable checkers across reverse dependencies and retains the evidence. Signature checks do not prove semantic, operational, data, or physical compatibility; testing all consumers has limits of access, cost, coverage, and future consumers. A dependency is the set of assumptions a consumer makes about a provider (operations, laws, effects, state formats, protocols, authority, resources, state meaning); content addressing cleans up identity and coexistence but not incompatible protocols or two versions managing one external state; different hashes can implement equivalent contracts and identical source can yield context-dependent artifacts. The real operation is checking and repairing obligations with reusable evidence.
- **Upgrade is a path through a version DAG.** With patch-style transitions a running system sits at a frontier and "any version to latest" is a path; transitions compose (T₁₃ = T₂₃ ∘ T₁₂ unless a cheaper direct one exists) only when intermediate preconditions and obligations hold, and the cheapest path depends on running state, resources, and active clients, not only on edges between version identifiers.
- **"Minimal diff" is several objectives:** bytes transferred; state examined or transformed; peak temporary storage; time unavailable; changes visible to users; old obligations disrupted. The smallest patch is not the least disruptive update; the floor on structural diff is semantic edit distance over the store.
- **"Best state preservation" has prerequisites:** state addressed by semantic identity, not position ([Store](store.md)); the needed information retained, else some new behavior begins only at a new time boundary ([Commitment](commitment.md)); obligations discharged or handed off without repeating external effects. Strategies: immediate translation, lazy conversion, adapters, per-session pinning, old continuations completing, replay of recorded inputs, expand/contract.
- **Fleet reality.** A fleet runs a version mixture during rollout; protocol compatibility across versions is a checked property (Avro and protobuf evolution rules are a checker nobody calls one); expand/contract is the fleet-scale divergence policy; version consistency may be promised per session rather than globally (Q20). Tested by [E3](../experiments/contract-change.md).

Ecosystem economics are in [Realization](realization.md).

## Residual obligations

After static analysis, specialization, allocation, and configuration, what remains to be checked or maintained dynamically? Some obligations become guards, some reservations, some physical isolation, some protocols; others disappear because their conditions are established for the whole region. An unresolved predicate becomes a runtime check where the missing information arrives: a residual cast in gradual typing, the residual program of partial evaluation, a guard with a deopt target, a conditional authorization result, a conditional claim from a checker, a checksum. Conditional permission and speculation with a guard are one mechanism; a denial policy and a fallback path still differ in semantics ([Justification](justification.md)). **Elimination licenses:** "arrival is periodic" eliminates timestamps; "single writer by wiring" eliminates authority checks; "no admitted contract change" eliminates history; "statically scheduled" eliminates progress tracking; "paths fixed at configuration" eliminates per-operation authority checks, after which changing the policy requires a transition. Each is a scoped commitment with a reason, visible in the editor as foreclosed options. "What does the runtime do?" becomes answerable per region instead of per language: the runtime is the residual obligations the compiler could not discharge, and a region with no residuals has no runtime ([E2](../experiments/three-realizations.md)).

## Self-application

The machinery that provides flexibility must itself be specializable and eliminable, or another expensive abstraction has been frozen into the substrate. The store is a representation choice; the controller hierarchy a scheduling choice; a timestamp a representation of ordering information; a version history retained information for particular future operations; a capability check one enforcement of an authority obligation; the IR and solver configuration replaceable artifacts with dependencies. In a stable region a timestamp is implicit in schedule position, authority in which route exists, a dependency in wiring, an interpretation rule in a datapath; none needs a runtime object merely because the semantic model contains it. Where dynamism prevents elimination, the information is represented explicitly. A universal logical model does not require universal per-operation overhead; this is what turned "every storage cell a versioned fact store, every transfer a timestamped packet" (C15, C24) into palette options instantiated where a region's admitted interactions require them ([Chipset family](../hardware/chipset-family.md)).

Which of the system's own models, histories, and decisions are materialized where is a placement problem: a microcontroller gets a specialized implementation and a compact configuration, not the derivation history; a server doing online adaptation keeps much more. Self-hosting means more than the compiler being written in its language: the stack represents and improves the process by which it constructs realizations, using its own workload models to decide whether a frequently used analysis deserves a better algorithm, a specialized structure, an accelerator, or a different deployment; it still needs a bootstrap implementation and evidence for replacing trusted components, and recovery when the optimizer itself fails is open (Q36). Each piece of bookkeeping present is justified by an admitted future interaction; each absent piece corresponds to an established fact that eliminated it.

Beyond software the same question appears with different actions and no assumption of reversibility or atomicity: replacing factory machinery while fulfilling orders, modifying a building while keeping areas usable, rerouting without violating active service commitments ([Realization](realization.md)). Open: Q15–Q22.
